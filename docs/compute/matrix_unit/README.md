# Matrix Unit diagrams and verification plan

This folder holds the figures for the [Matrix Unit I/O scheme](../matrix_unit_io_scheme.md).
They cover the Matrix Unit only: `bpu_sa_sram_wrapper` and everything under it, plus the
`sram_arbiter` matrix port it talks to. The SVGs in [svg/](svg) are generated; regenerate them whenever a port or
parameter changes. [png/](png) holds PNG copies of the same figures, for chat and slides.
Keep each PNG synchronized with its SVG. The ports, module cards, hierarchy, structure and
timeline show the earlier dedicated write-completion input (`matrix_wr_done_i`, `WriteAcks`),
which the fixed next-edge write commit has since removed.
**Stale:** they predate the logical M/N ports, the output-encoding fields, `cmd_decode_error_i`,
`milestone_inc_o`, `bpu_sa_output_convert` and `bpu_sa_command_decoder`; regenerate them
before relying on the port and module figures.

**Regression modes** (`tb/compute/Matrix_Unit/run_tests.sh`, VCS):
- **Default:** every run must pass.
- **`--inject-failure`:** every testbench corrupts one expected value, so every run must fail.
- **`--check-reset-guard`:** must fail with `active-reset precondition not reached`.
- **`--check-write-reset-guard`:** must fail with `pending-write reset precondition not reached`.

The wrapper testbench also covers logical shapes with junk outside M × N, short final scale
blocks, output encodings 1–4 at their packed sizes, milestone counts and decode errors.

The default runner plans 75 configuration/seed pairs across 27 configurations. These counts
describe the selected tests; results for a revision belong in its generated summary and logs.

**The arbiter model** follows the [arbiter I/O scheme](../../memory/sram_arbiter_io_scheme.md):
- random request ready, a read-response latency, and writes that commit on the edge after
  acceptance;
- one response pulse per read, in request order, with no backpressure;
- no write acknowledgment: write payload capture on the accepting edge and the SRAM update
  on the next edge; reset cancels a write not yet committed;
- random garbage in the bytes a read didn't ask for.

It checks the request protocol:
- a stalled request is still offered, unchanged, at the next edge;
- `req_valid` is never X or Z;
- addresses are row aligned, and `size_bytes` is in 1–512;
- reads stay inside the A, B and scale-table regions, and writes stay inside C with no X or Z bytes.

Write-completion checking distinguishes accepted write requests from writes committed in SRAM.
The wrapper must remain busy and reject the next command until its final write completes.

**Not covered yet:**
- coverage measurement;
- formal proofs, such as of the credit and ordering rules on the structure diagram;
- X propagation, since stimulus is two-state;
- integration with the real `sram_arbiter`;
- the command source, which is defined outside this unit.
