# Spec style guide

The spec is the contract between design and verification. Verification builds its model from the spec, not from the RTL.

Template: `../templates/block-spec-template.md`

## Rules

- **S1.** Fill in every template section. Write "None." where a section does not apply.
- **S2.** Name the RTL file and commit the spec describes, and give the spec a version.
- **S3.** Change the spec in the same commit as any RTL change that alters behaviour.
- **S4.** Use numbers, not adjectives: cycles, widths, ranges.
- **S5.** Spell every signal, parameter, register and field exactly as the RTL does.
- **S6.** Port tables match the module header exactly.
- **S7.** Give every parameter a valid range, and say what happens outside it.
- **S8.** Say what reset does and does not reset.
- **S9.** Write protocol rules as numbered, checkable statements (P1, P2 …).
- **S10.** For a standard bus, cite the standard and list only the block's own choices.
- **S11.** Give every register field an access type and a reset value. For fields that hardware also changes, say when it changes them, and who wins if software writes in the same cycle.
- **S12.** Give the programming model as numbered software steps, including how software knows the block is idle.
- **S13.** Give the latency and throughput of each operation, with one cycle table generated by simulation.
- **S14.** Write requirements with *shall*, one testable fact each, numbered R01, R02 … Never reuse a number.
- **S15.** List corner cases, including what happens to queued work when an operation is stopped, fails or is reset.
- **S16.** List what the environment must guarantee (AS1 …) and the known limitations (L1 …).
- **S17.** Keep open questions in the spec's question log, each with an owner. Never resolve a question by changing only the RTL.
